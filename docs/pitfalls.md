# 踩坑实录

> 这份文件收录搭建和运维这套网络环境时**真实踩过的坑**。每个坑都付出了几小时到几天的代价。
> 脱敏说明：涉及的 IP、凭证、供应商名称均已隐去或泛化，不影响教训本身。
> 给 AI 的提示：引导用户施工时，每进入一个相关阶段，主动把对应坑的教训讲一遍。

---

## 坑 1：给路由器下错发行包——musl 和 glibc 不是一回事

**现象**：在 MT3600BE 上装 sing-box，下载了官方 release 的 `linux-arm64` 包，解压、赋权、运行，直接报错起不来。排查了半天 Reality 参数和配置 JSON，全是对的。

**根因**：那个 `linux-arm64` 资产动态链接到 **glibc** 装载器（`/lib/ld-linux-aarch64.so.1`），而 OpenWrt 用的是 **musl**（`/lib/ld-musl-aarch64.so.1`）。架构对、libc 不对，一样跑不起来。换 `linux-arm64-musl` 资产后一次成功。

**教训**：

- 在 OpenWrt 上装任何预编译二进制，先确认 libc：musl 系统必须用 musl 版资产
- 报错先怀疑"资产选错"，别先怀疑配置——那次浪费的排查时间全在错的方向上
- 同理：OpenWrt 的 opkg 源里**没有** sing-box 包，不要指望 `opkg install`，老老实实下官方 release

## 坑 2：OpenWrt 没有 nohup（也没有 bash、perl、python）

**现象**：做 fail-closed 测试时需要"停掉 sing-box → 验证断网 → 延时自动拉起"。初版脚本用 `nohup` 挂了个延时任务，结果 sing-box 停了之后**没有被拉起来**，第一次自动恢复测试直接失败，只能手动救。

**根因**：OpenWrt 默认 shell 是 BusyBox **ash**，没有 `nohup`。后来改成在同一个 SSH 会话里保持远端 shell 存活、用后台子进程执行延时 `start`，才跑通。

同类的坑还踩过两个：修复脚本写成 bash 语法，路由器上 `ash: bash: not found`；让执行侧用 `perl` 改文件，路由器上没有 perl。

**教训**：

- 路由器上写脚本只用 POSIX `sh`，别假设任何 GNU 工具存在
- 改文件用 `cat` heredoc 或 `vi`，不要假设有 `perl` / `python` / `sed -i` 的高级用法
- "临时挂后台进程"这种在 Linux 桌面上的肌肉记忆，到 OpenWrt 上先验证再依赖

## 坑 3：本机代理客户端三层劫持——退出即断网，连踩三次

**现象**：电脑上装着本机代理客户端（v2rayN 一类）。每次退出它，电脑立刻断网。同一个症状**反复出现了 3 次**才彻底修干净。

**根因**：这类客户端运行时同时劫持三层：

1. **DNS**（改成它自己的本地监听地址）——第一次修复时清了
2. **系统代理**（HTTP/HTTPS/SOCKS 全指向 `127.0.0.1` 的本地端口）——**第一次漏查了**
3. **路由表**（TUN 虚拟网卡）——退出时通常自动恢复

客户端一退出，本地端口没人监听，所有走系统代理的流量（浏览器、一堆系统服务）集体暴毙。只修第一层当然治标不治本。

**教训**：

- 排查"退出代理就断网"，**DNS + 系统代理 + 路由表三层必须一起查**，修一层就收尾等于没修
- macOS 上清系统代理：`networksetup -setwebproxystate Wi-Fi off`（HTTPS/SOCKS 同理），清完用 `scutil --proxy` 确认三项 Enable 全为 0
- 最干净的纪律：**连上 MT3600BE 之后，本机任何代理/VPN 客户端一律不装、不开**——路由器已经透明接管全部出海流量，本机代理只会制造冲突

## 坑 4：DNS 被污染，chatgpt.com 解析到了 Facebook 的 IP

**现象**：手机连路由器 WiFi，ChatGPT 死活打不开；Mac 上手动把 DNS 改成公共 DNS 的设备却没事。

**根因**：路由器 dnsmasq 的上游用的是上级路由分配的 DNS，查询走明文 UDP 53 直连，被链路污染注入假应答。实测污染的离谱程度：

- `chatgpt.com` 解析到的是 **Facebook/Meta** 的 IP
- `api.openai.com` 解析到的是 **Twitter/X** 的 IP

更阴的是第二个 bug：TPROXY 入口没开 SNI 嗅探（`sniff` + `sniff_override_destination`），流量即使被透明接管了，也是盲代理到那个假 IP，TLS 握手必然失败。也就是说就算污染发生了，隧道本来有机会靠 SNI 纠正目的地，但这个保险当时没装。

**教训**：

- 明文 UDP 53 在污染链路上**没有任何可信度**，唯一可靠的防御是 DNS 走加密通道（加密 DNS / 走隧道解析）
- 修复要双保险：源头用干净上游 + TPROXY 开 SNI 嗅探兜底纠正
- 症状是"某个设备打不开某站、换个设备又正常"时，先怀疑 DNS，别怀疑 App

## 坑 5：固定 IP 忘续费，IP 直接被回收

**现象**：某天发现住宅 IP 代理不工作了。查后台：订阅过期没续。联系客服，答复干脆利落——**旧 IP 已释放，无法重新分配**。

**后果**：只能重新买订阅、新建代理用户、拿到一个全新的 IP，然后 VPS 配置、本机期望出口 IP 文件、全部验收项重跑一遍。这还没完：付款过程中两笔扣款（两个不同支付渠道）和客服扯皮了好几轮。凌晨两三点开始处理，折腾到天亮。

**最深的代价不是钱**：平台会把"账号 ↔ IP"的绑定记进风控档案。被迫换 IP 等于账号环境的一次硬变更，之前养的稳定性部分清零。

**教训**：

- 所有订阅（VPS + 住宅 IP）**下单当天就开自动续费**
- 日历再加到期前 7 天 / 前 1 天双重提醒——自动续费也会扣款失败
- 代理凭证改过一次之后，记得 VPS 配置、本机哨兵文件要同步改（这次恢复时这块倒是做对了）

## 坑 6：IP 段被平台专有信号源标记，通用查分查不出来

**现象**：一个 AI 平台的账号持续被"降智"（回答质量肉眼可见地变傻）。换全新住宅 IP、深度清理设备标识，全都没用。查通用 IP 信誉库：分数好得很（IPQS 只有 3 分，接近满分干净）。

**根因**：该平台用的是**专有信号源**，早就把那个供应商的整个 IP 段标记了。通用风控库不标、IPQS 不标，但平台自己标。也就是说同一段 IP 对另一家平台完全干净、唯独这家平台视为脏——两家风控互相独立。

**定位方法（这个实验是全文最值钱的部分）**：**A/B 换 IP 实验**。同账号、同设备、同样的问题，只把出口切到另一条线路——立刻恢复正常。一次实验就把"设备问题/账号问题/IP 问题"三个嫌疑犯里的真凶钉死。

**后续**：全家出口迁移到另一家供应商的独享 ISP IP（换供应商 = 换 IP 段），老账号恢复正常。

**教训**：

- 遇到降智/封号，**第一个动作是 A/B 换 IP**——这是最便宜的判别实验，别先拆设备（那次先花大力气清了整台 Mac 的设备标识，全是无效功）
- 通用查分（IPQS 等）只是初筛，**平台专有标记查不出来**，A/B 对比才是终审
- "换槽位不换段 = 没换"：同供应商内换另一个 IP，如果还在同一个被标记的段里，等于白换
- 所以采购住宅 IP 时，到手先做 A/B 验证再投入养号（见 `docs/shopping.md`）

## 坑 7：临时方案变长期——本机应急代理成了混合态，还引来安全事故

**现象**：一次路由器 DNS 链断裂（dnscrypt-proxy 和 dnsmasq 抢端口，双双起不来），为了不断网工作，在本机临时起了个 sing-box + 设了系统代理先顶着。

**然后就没有然后了**。路由器没修，"临时"方案变成了长期状态：Mac 处于"一半走路由器透明代理、一半走本机代理"的混合态，没人说得清流量到底走哪条。几天后大扫除时发现的状态触目惊心：网关漂移、系统代理指向本机端口、本机 sing-box 还配了 launchd 开机自启——而在此期间，一个恶意编辑器扩展趁乱被装进来，往系统钥匙串塞了一个带 MITM 能力的根证书。

**根因**：不是技术问题，是纪律问题。**应急方案没有拆除期限，就会变成永久状态**——而且因为它"能用"，你失去了修复主线（路由器）的紧迫感。

**教训**：

- 任何应急/临时方案，启用时**当场定拆除条件**（比如"主线恢复后 24 小时内拆除"），写进待办
- 应急方案用完后按清单完整拆除：进程、配置、系统代理、开机自启项，一项不留
- 网络处于"说不清的混合态"时，不要做账号操作，也不要装新软件——混乱面是安全事故的温床

## 坑 8：七小时的误诊——根因在网络层，却在应用层修了 7 小时

**现象**：一次路由器配置变更后，两个桌面 IDE 同时挂掉：提问无响应、`Internal Error`、甚至提示"安装已损坏请重装"。

**修复过程（反面教材）**：负责修复的 AI 把问题误判为"应用自身故障"，在应用层打了约 7 小时补丁：改应用配置、注入 DNS hook、改扩展宿主文件、换内置扩展目录、重建会话存储……结果越修越烂——一个 IDE 真的报"安装损坏"（因为改了应用包内文件），另一个的模型选择器 UI 被修没了。用户原话："我怎么感觉你越修越垃圾呢。"

**实际根因**：路由器配置变更的副作用带坏了本机的透明 DNS 链路——IP 级 TCP 出海是通的，但系统域名解析全挂。真正有效的修复（收窄一条过宽的 DNS 规则 + 清掉残留的代理配置）**只花了 10 分钟**。

**教训**：

- "海外链路能出海、但应用报域名解析失败"这个组合，**先怀疑 DNS 解析层，不要先怀疑应用**
- 修复前先做分层验证：系统 DNS → 应用内 DNS → 到目标的连接，哪层坏了修哪层
- "报错变少了"不等于"恢复了"——恢复判定必须基于功能验证（能发消息、能收到回复）
- 应用包内文件、内置扩展、状态数据库，不是根因就别碰——修了只会制造新问题
- 网络变更后必须当场跑验证探针再收工；那次事故的 7 小时里，有 6 小时 50 分是在为"变更后没验证"还债

---

## 元教训：这些坑的共同结构

1. **"能跑"和"对的"之间隔着一次验证**：每个坑在"改动完成"那一刻看起来都是好的，全是验证缺失或验证太晚
2. **环境假设是头号杀手**：假设有 bash、假设有 nohup、假设源里有包、假设查分网站等于平台视角——在陌生环境（OpenWrt、供应商后台、平台风控）里，先验证假设再行动
3. **账号环境的稳定性是复利，事故是单利**：换 IP、换段、混合态这些"硬变更"每一次都在消耗养号积累。所有纪律（固定 IP、续费提醒、不用本机代理）的本质都是减少硬变更次数
